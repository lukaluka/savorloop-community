# Contributing useful feedback and documentation

Thank you for helping make SavorLoop easier to understand and use. Good contributions include clear bug reproductions, accessibility reports, corrections to a guide, and specific descriptions of a user need.

## Start with the user-facing problem

Use [SUPPORT.md](SUPPORT.md) to choose a ticket type. Explain the task you were trying to complete, what happened, and the result you expected. Search existing issues first. Keep private information and personal exports out of all ordinary issues and pull requests.

For a feature idea, describe the problem and the practical benefit before proposing an implementation. An accepted idea is not a promise that it will ship. This repository does not accept private app source, signing material, food databases, or personal datasets as contributions.

## Documentation changes

Small corrections can be proposed through a pull request. Link the relevant issue when one exists. Use plain language, exact labels from the current app, descriptive links, and accessible structure. Explain which build or evidence supports a changed instruction. Do not describe a planned feature as shipped or remove a limitation merely because it is inconvenient.

Submit only material you have the right to share publicly. Do not copy a third-party article, proprietary support guide, or publisher database into the repository. The content/reuse notice does not grant rights to the application or to third-party data.

## How documentation stays current

The maintainers keep the canonical support pages alongside app development. Relevant completed product changes must include a review of user-facing instructions, known limitations, support forms, and the changelog. Only the reviewed public-support files are published here, with a separate documentation history.

Public contributions are reviewed and incorporated into that canonical documentation before publication. A maintainer may close a proposed change after publishing its equivalent from the canonical source, with an explanation. This avoids a later automatic update overwriting an accepted correction.

No public issue or pull-request content is automatically executed, applied to the app, or used to authorize access to private code. Repository workflows are disabled for this documentation-only support hub. Maintainers should review contributions as untrusted input, including links and attachments.

## Review checklist

- Instructions match the current feature and its actual labels.
- Availability and known limits are accurate.
- Links work, and the change remains readable without images.
- Examples contain no real health, account, or payment data.
- No private paths, application source, credentials, or internal records were included.
- Significant user-facing corrections include a changelog entry.

Follow [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md). Security issues use [SECURITY.md](SECURITY.md), even if a public code change would appear to fix them.
